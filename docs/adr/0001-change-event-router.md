# Client cache coherence runs through a `ChangeEventRouter`, not ad-hoc callbacks

A `ChangeEventRouter` owns the client-side cache-coherence pipeline: each push-capable `Connection` registers as its source on construction and calls `router.accept(ChangeEvent)` for every server-initiated push; each push-fed `RemoteTable` calls `router.bind(db, table, this)` on creation and receives events back as `applyChangeEvent(event)`, where it deserialises the value with its own `Fory` + `valueClass` and either `cache.put` (writes) or `cache.invalidate` (deletes). `Connection.supportsInvalidation()` is removed in favour of `router.hasSource()`; the `setInvalidationCallback` setter on `TcpConnection` and the `handleInvalidation` method on `RemoteRoot` both disappear. The previous shape — a key/db/table tuple emitted on a per-connection callback, with the value bytes thrown away — silently degraded server `SET`s into client cache misses; the router preserves the value and keeps client behaviour symmetric with the server-downstream `EdgeHandler` / `RelayHandler` paths.

## Considered Options

- **Pure refactor: keep value-dropping behaviour, rename the callback into a module.** Rejected: leaves the bug (every server SET = client cache miss on next GET, even though the push frame carries the new value). The audit's deletion-test motivation requires the module to *change* behaviour, not just relabel it.
- **Typed event stream (`subscribe(Consumer<ChangeEvent>)`) with `RemoteRoot` still routing.** Rejected: equivalent to renaming the existing setter. `RemoteRoot` would keep the `(db,table) → RemoteTable` map and the dispatch logic, which is exactly the locality we want to move into the new module.
- **Router owns the `RemoteTable` registry entirely** (`RemoteTable` construction goes through it). Rejected: bundles two concerns — table-instance management and event dispatch — into one module. `RemoteRoot` keeps table construction; the router only routes.
- **Decode `ChangeEvent` payload bytes inside the router.** Rejected: each transport (TCP, future HTTP-push or gRPC) knows its own wire format. Decoding inside the router would force every new transport to teach it a wire — the opposite of cross-transport-ready.
- **Router decodes values to a generic `Object`.** Rejected: loses type fidelity. `RemoteTable<K,V>` already owns the `Fory` instance and `valueClass` used for `GET`-response decode; reusing that path is the symmetric, type-safe choice.
- **Keep `Connection.supportsInvalidation()` as a boolean flag.** Rejected: the boolean is a parallel data point to "is there a source registered with the router?". Two truths for one fact decay; we collapse to one — registration.
- **Per-key worker dispatch from day one** (mirror server's `keyWorkers[hash(key)]`). Rejected as premature; we keep synchronous dispatch on the source thread. If profiling shows the TCP reader thread blocking on `Fory` deserialisation under load, we promote to per-key workers as a follow-up. The router's interface (`accept(event)`) does not change between the two implementations.

## Consequences

- `bonsai.ChangeEvent` (already defined in the shared protocol module) becomes the canonical type on the client receive side. `TcpConnection.readLoop` decodes a push frame into a full `ChangeEvent` (including value bytes + `isDelete`) instead of synthesising a `(db, table, key)` tuple.
- `RemoteRoot` shrinks: its `invalidationCallbackRegistered` lazy-init, its `handleInvalidation` method, and its setup of the connection's invalidation callback all collapse into "construct a `ChangeEventRouter`; let the connection register itself; let `RemoteTable` bind itself".
- The "is client cache safe on this transport?" decision (today, `connection.supportsInvalidation()` inside `RemoteRoot.use(...)`) becomes `router.hasSource()`. Adding a new push-capable transport in future means *the transport registers itself with the router*; no enum, no flag, no per-call-site fork.
- `RemoteTable.applyChangeEvent(ChangeEvent)` is the seam against which the integration test asserts: server `SET` → client cache holds the new value (no subsequent miss); server `DELETE` → cache invalidates; wrong-table event → no cross-fire.
